## B. Decisions made

**OB vs displacement-origin zone (resolves the remaining ambiguity, not just
the earlier policy ruling):** both approaches are now fully deterministic.
Approach A gets a fixed 5-bar lookback, a "nearest opposing candle" anchor
rule (no ambiguity — scanning stops at the first match), explicit full-range/
body-only boundary formulas for both directions, a precise touch/confirmation/
invalidation definition, and expiry at the end of the zone's own session
segment (reusing existing segmentation rather than inventing a bar-count
constant). Approach B is defined as deriving its zone from D1 directly with no
anchor search — explicitly non-equivalent, since it can never have a
"no anchor" case while A can. **Recommendation unchanged: Approach B (simpler)
is the v1 default**, overturned only by the §7.5 comparison.

**Zone comparison, made scientifically fair:** one controlled run across four
configurations (A-full, A-body, B-full, B-body), same data/code/costs/rules
throughout, varying only the zone source and boundary type. Set a concrete
minimum-evidence bar — **≥100 qualified setups per configuration** — below
which the result is `INCONCLUSIVE` and Approach B is retained by default. This
was the one piece of vagueness I most wanted to remove: "insufficient evidence"
had no number before this revision.

**Ranking methodology:** replaced the placeholder weighted-score idea with
**four mandatory pass/fail gates** (trend alignment, relative strength,
structure confirmation, qualifying displacement) and one optional feature
(volume, only when a baseline exists). No invented weights or normalization —
rank within a direction by relative-strength magnitude, tie-broken by
displacement recency. This is deterministic and needs no backtest to run; the
backtest is what later tells us whether weighting would help, not something
assumed now.

**Historical-data / validation sequencing:** split Gate 4 (needs a batch
historical dataset — no live streaming required) from Gate 0 (live SmartAPI
streaming, needed later for Gate 5). Stated plainly that **no historical data
source is yet confirmed** as sufficient — this was previously an unstated
assumption, now an explicit blocker with a minimum next action (a bounded test
pull against SmartAPI's historical endpoint, or an approved alternative).

**Other material decisions:** split the Definition of Done into acceptance
criteria (§12.1, objectively testable), categorized status (§12.2 — separates
deterministic requirements from hypotheses, validation requirements and
deferred features), and DoD proper (§12.3) — so the document stops implying
every provisional number must be proven before a single line of code is written.

the specification as written.

## One place I'd flag as possibly too strict (per the owner's invitation)

The §7.5 minimum-evidence bar of **100 qualified setups per configuration**
(400 total across the four configurations) is my own concrete number, chosen
to avoid "insufficient sample" being vague — but I have no empirical basis yet
for whether 100 is the right bar for this specific displacement+zone
combination's expected frequency on 50 symbols. If Gate 0's data audit later
shows qualifying setups are much rarer than assumed, 100-per-configuration
could itself become a blocker requiring many months of history just to reach
the evidence bar. I'd rather flag this now than have it silently become a
reason to either wait too long or lower the bar without noticing. Recommend
revisiting this specific number once real displacement frequency is observed
from Gate 0, rather than locking it as a permanent standard.
